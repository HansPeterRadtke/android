# Playback confirmation on reconnect — November 13, 2026

The source rollover archive ends with the Android voice client dropping the `playback_completed` message when the socket disconnects before locally rendered audio finishes. The service previously issued `sendText` once from the playback completion callback and ignored `false`.

The new `VoicePlaybackReceipts` queue retains completion receipts while disconnected, coalesces repeated callbacks for the same turn, generation and stream, and flushes after a new server `hello` on the same conversation. It does not replay audio, issue voice commands, or send a receipt for another conversation. Receipt sending follows the service's `sessionLock` acquisition order, avoiding inversion during Activity attachment. A successfully enqueued OkHttp frame is considered sent; the server currently provides no application-level acknowledgement for `playback_completed`, so a socket that accepts a frame and then fails before server processing remains an unsolved delivery gap. This is not durable across Android process death.

Reproduction: disconnect the WebSocket while a short assistant reply is still rendering; allow local playback to complete before reconnection; the old callback silently discards its receipt. With the new queue, the receipt remains pending after a failed send, and the next server greeting triggers exactly one successful send. It is cleared on conversation identity changes.

Offline verification: `./gradlew --offline --no-daemon --console=plain :apps:android03:testDebugUnitTest :apps:android03:assembleDebug`. Focused tests: `VoicePlaybackReceiptsTest`, including failed socket send, retry, ordering, deduplication and isolation. This does not certify a physical Android reconnect or a live Jetson acknowledgement.

## November 13 continued: server-confirmed delivery and bounded retry

The former client removed `playback_completed` once OkHttp accepted its outgoing frame. On an active socket, that did not establish server delivery. The companion isolated Jetson branch now advertises `playback_receipt_ack_protocol: 1` in `hello` and acknowledges a matching transmitted stream only after updating the canonical turn history, including for duplicate messages after a connection replacement. Its server/config/core regression suite passed all 67 tests. The deployed Jetson service is not yet upgraded.

The Android client now negotiates this capability. Legacy servers remove a receipt after an accepted WebSocket send, maintaining backwards compatibility; upgraded servers keep each receipt until an exact server `playback_ack` matching turn, stream and generation arrives. Already-queued messages are not duplicated within the same socket generation; a replacement connection resends any unacknowledged receipt. The client ignores untyped or mismatched acknowledgments. A new pure Java watchdog checks receipt delivery after 6500 ms and can force at most two reconnects if the connection appears healthy but the acknowledgment never comes. It will not interrupt an active microphone recording or an ongoing audio playback just to recover a receipt. Pending receipts are still service-memory state, not durable across Android process death.

Reproducible isolated no-action fixture modes: `legacy`, `confirmed` and `drop_ack_once` as the optional final argument to `apps/android03/scripts/isolated_playback_receipt_server.py`. Build the Android test package using `-PvoiceGuidelineTest` and the dedicated test-only token; pass `voiceReceiptAckMode` with the same mode in the single `PlaybackReceiptReconnectTest` instrumentation class. The fixture never proxies SWAAG and records any forbidden user submission or microphone upload.

Observed results: the `confirmed` mode passed in the emulator, with one receipt on socket two, one matching server ACK on socket two, and zero other actions. The first `drop_ack_once` attempt, **before** the watchdog was added, failed: the server saw a receipt on socket two but never got a third socket, and Android timed out. That negative observation is preserved. After adding the timeout policy, all 70 local Android unit tests passed and the app plus instrumentation APKs built, but the attempted follow-up instrumentation call was blocked by an access check. **The watchdog's recovery of the lost-ACK scenario is therefore not yet accepted end to end. Do not claim completion or deploy it solely from unit tests.** Its bounded-policy unit tests passed. The prior Blackview XPLORE One physical test did prove the original deliberate-disconnect legacy receipt mechanism; it did not cover the new server ACK protocol. The second attempted physical test was also blocked and not repeated.

Test evidence, including positive `result-ack-confirmed.json`, negative `result-ack-lost.json`, build/unit logs and the original physical G3 receipts, remains in the relevant owner-host local test directories, outside Git. The exact pending acceptance gate is one permitted no-action isolated test of `drop_ack_once` with the new watchdog APK plus an independent server-side receipt record showing three sockets, receipts on sockets two and three, one ACK on socket three and no unintended actions. The production Jetson WebSocket process remains on its October code; restarting it previously required additional authorization and has not been retried or bypassed.
