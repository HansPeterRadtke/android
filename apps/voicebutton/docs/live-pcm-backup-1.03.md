# Voice Button 1.03 — fsynced PCM backup during active recording

The normal microphone capture path and bounded PCM writer are unchanged. The writer fsyncs an append-only PCM journal, then publishes a nonblocking progress notification to an independent low-priority worker. That worker sends at most 64 KiB per HTTP part with a SHA-256 proof and an exact offset. The Jetson receiver fsyncs the raw part and its metadata before acknowledging the byte count. Missing or changed acknowledgments are reconciled against the receiver's actual durable offset. No MP3 conversion, TCP write, or HTTP request is performed on the urgent AudioRecord thread or PCM writer.

The live PCM mirror uses separate, authenticated `/audio/v2/live-pcm-status` and `/audio/v2/live-pcm-part` endpoints. The phone must have a valid recording-server access token saved through More → Recording server access. The receiver never accepts the raw microphone feed without that token, including during legacy upload compatibility. On an unpaired phone, the UI must state that raw live backup requires pairing; the recording remains locally durable. The automatic-upload setting and explicit Exit stop the raw worker. Neither failed live replication nor the lack of pairing blocks locally fsynced microphone capture.

While recording, the main backup bar shows authenticated server-durable raw PCM bytes divided by locally-fsynced PCM bytes already captured, not future audio. After pause or finish it reverts to ordinary verified MP3 chunks and final commit. These are different scopes, displayed with different labels. Current recording bytes are not described as backed up before a durable receiver acknowledgement.

The canonical recording remains the encoded MP3 made after capture, with a manifest of completed MP3 chunks. The raw mirror is a secondary recovery source, not an independently committed MP3, and is not automatically transcribed. The receiver has an offline recovery tool to convert an existing mirrored PCM stream to private WAV files without editing the originals or user session metadata. Jetson reserves at least 10 GiB free disk space and returns HTTP 507 when raw backup storage would violate it. The app reports that this delays live backup without implying that phone audio has been lost.

Regression tests cover phone-side unauthorized refusal, private token and part hash transmission, worker publication without blocking the writer, observed server-acknowledged byte progress, resumed/duplicate/conflicting offsets, low-space behavior and bit-accurate WAV recovery. Unit/instrumentation compilation and lint alone do not prove that the physical Ulefone's microphone, network and power management continue to work during an extended real recording. Phone acceptance remains necessary. An app update alone cannot install or provision the private token on a phone not connected to the development environment.

## Version 1.04 — follow-up audit

A rapid pause/resume or switch to another recording previously cleared the in-memory live-PCM backup targets and could silently abandon an older session's fsynced but unacknowledged PCM prefix. The replicator now retains all unacknowledged targets across recording changes and still accepts the final durable journal-close callback from a previously active session. Even a fully acknowledged `.open.pcm` target remains eligible for its unsynced final tail until it is actually closed, so its last bytes are not lost from the remote-backup queue. Only fully acknowledged closed journals may be pruned. The canonical post-pause MP3 journal and transfer logic are unchanged.

Another progress-integrity defect was that a raw status GET could supply a remote offset beyond the locally fsynced prefix, letting the client incorrectly conclude that no further backup was necessary. The receiver proof is now checked against the exact session, sequence, sample rate, durable flag, server identity and local byte bound before the offset is accepted. Regression tests cover wrong identities, false durable flags, mismatched sample rates, impossible server offsets, rapid session switches and delayed final journal closure.

The recording writer's callback mutex previously also covered the SharedPreferences pairing lookup at `begin`; that lookup now happens outside the writer-facing lock. The writer callback still performs no network I/O or MP3 conversion. As before, real handset testing with the private recording-server token remains necessary for an end-to-end live backup claim.
