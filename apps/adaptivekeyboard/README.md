# KontextTastatur — local adaptive German Android IME

A standalone Android InputMethodService for German QWERTZ typing, focused on user-confirmed contextual predictions. This project is developed in a separate Android repository worktree to avoid disturbing the existing Android clients.

## Implementation and privacy contract

- Three independent suggestions, in rank order **second, first, third**, so the most probable appears in the center. No forced autocorrection or automatic acceptance.
- Predictions are based on mixed German and English lexical frequency and user-confirmed word frequency, previous-word and previous-two-word context, and exact user-selected prefix/word combinations. Word forms are keyed with `Locale.GERMAN` case folding; user-confirmed spelling and canonical German noun casing are preserved.
- The UI calls `predict` after a text insertion; a visible or discarded suggestion does **not** increase any count. A typed word is learned only when the IME sees a delimiter or the user explicitly taps a suggestion. The latter replaces the typed prefix, inserts a space and records the exact selection separately. Immediate deletion of a delimiter attempts to undo the most recent learning event.
- Personalization is locally persisted in `learned.db` (SQLite) in the keyboard app's private data directory, without raw typed sentences, text-field dumps or cloud syncing. Database writes are serialized on a worker thread. Android backup is disabled. Only local context words and count statistics are retained, including a prefix when the user explicitly selects a completion. Other apps can access keyboard output only through the normal Android input method API.
- Passwords, sensitive text variations, URL/email fields, `NO_SUGGESTIONS`, `IME_FLAG_NO_PERSONALIZED_LEARNING`, and non-text fields disable learning and suggestions. Manual private mode disables both learning and suggestions globally. Users can explicitly reset learned data; the bundled lexicon remains.
- German and English completion, user-typed capitalization (lowercase, uppercase or all caps), contractions, learned rejection of suggestions contradicted by further typing, German umlauts, sharp S, uppercase ẞ, symbols, alternate accented letters via long press, emoji categories, cursor movement, copy/cut/paste, manual clipboard pinning and local clipboard history (twenty entries, up to three thousand characters) are supported.
- GIF search is only performed after explicitly entering the GIF search panel and pressing search. No API key is needed for the default Openverse search of Wikimedia Commons animated GIFs. GIPHY is an optional, much broader provider requiring its own user-provided API key. No secret key is included in the APK. GIF thumbnails are fetched from the selected provider, and a selected GIF is committed with Android `InputConnection.commitContent` using a read-only `content://` provider if the receiving app advertises `image/gif` support. Otherwise the public GIF link is committed as text. Original data and provider attributions appear in the settings. GIF search and sharing require connection; typing and prediction do not.

## Build and install

From the Android repository root:

```sh
ANDROID_HOME=/data/install/android-sdk ./gradlew :apps:adaptivekeyboard:assembleDebug
ANDROID_HOME=/data/install/android-sdk ./gradlew :apps:adaptivekeyboard:testDebugUnitTest
adb install -r apps/adaptivekeyboard/app/build/outputs/apk/debug/adaptivekeyboard-debug.apk
```

Open the launcher activity and enable/select `KontextTastatur` using the two system controls. Do not switch the owner's real-phone default keyboard without approval. Emulator testing uses API thirty-four and does not change any physical device.

## November 7: GIF sharing correction, version 0.4.0

Owner reproduced the broken GIF behavior by posting two Wikimedia Commons description-page links, page IDs 7419763 and 7399044, in a conversation. The original fallback in `AdaptiveKeyboardService.sendGif()` inserted `gif.link` via `InputConnection.commitText()` when the receiving text field did not advertise support for `image/gif`. That was a fundamental format error: a landing-page URL is not an animated attachment. Both reported pages are real GIFs: `Scratch-Lissajous-nevit-01.gif` and `Scratch_Rainbow_nevit.gif`.

The corrected behavior is as follows. On tapping a result, the keyboard downloads and validates the original GIF bytes into its private cache. If the receiving editor advertises image support, it attempts `InputConnection.commitContent` with a read-only temporary URI grant. Otherwise, or when the editor rejects the request, it launches the Android binary image sharesheet with `ACTION_SEND`, MIME `image/gif`, `EXTRA_STREAM` as a `content://` URI, `ClipData`, and `FLAG_GRANT_READ_URI_PERMISSION`. **It never silently inserts the Wikimedia landing-page address.** A long-press on a result also offers **share GIF as a file** and **copy GIF to clipboard as image data**. The custom content provider reports filename and size via `OpenableColumns`, enforces read-only access and only exposes matching cached `.gif` items. The app and user must still choose a destination in Android's sharesheet: the keyboard cannot force rich insertion into apps which do not implement Android image-keyboard integration. Sharing to a destination app may start a new conversation instead of adding the GIF to the existing text field. The keyboard does not claim otherwise.

**Verified emulator acceptance:** Android API 34, user-initiated `scratch` GIF search through Openverse; first result resolved to the user's *Scratch Rainbow nevit* GIF and was cached as a 13,877-byte GIF image, 180 by 661 pixels, matching Wikimedia's original metadata. Tapping that result from the plain-text Settings test input launched the system `ChooserActivity` with an `image/gif` ClipData payload, temporary read permission, and `ACTION_SEND` image attachment. Android's sharesheet displayed **Sharing image** and a proper visual preview of the GIF, not text or a Wikimedia link. `GifDeliveryPolicyTest` verifies that plain-text/unsupported editors route to binary sharing and that compatible MIME types take the direct path. Together with the unchanged prediction tests there are 25 passing JVM tests.

**Still not claimed:** attaching into the current ChatGPT input field, or end-to-end delivery to WhatsApp or another real messaging recipient, was not verified because this depends on the target app's support and user selection. It is not possible for an IME to make a plain-text-only editor accept binary GIF data just by sending more text. No real user messages were sent in testing.

## November 7: GIF preview-loading repair (v0.5.0)

Owner reported that GIFs still did not load. Analysis of the shipped code found a systematic failure: anonymous Openverse search returns `api.openverse.org` preview proxy addresses, which sometimes return HTTP 424, and the fallback rejected original GIFs above 1.8 MB. There was also one shared three-thread executor for search, previews and user-selected shares; a tap could wait behind up to eighteen thumbnail requests. Errors were silently presented as empty tiles.

The corrected version constructs Wikimedia's canonical `120px-*.gif` thumbnail URL when the original URL is a legitimate `upload.wikimedia.org` GIF, with a strict origin/path check and preservation of raw URL encoding. If Openverse search is unavailable or gives unusable results, its independent Wikimedia Commons image-information search provides a fallback. Thumbnail requests have shorter bounded timeouts and a small in-memory LRU; previews are downsampled for UI memory and `AnimatedImageDrawable.start()` enables animation on Android versions supporting it. Ten results are fetched initially, each tile always displays its name, and the toolbar reports real completed/success/failed thumbnail counts. Search, preview and user-selected GIF transfers now have separate workers, so an image-sharing tap does not queue behind background thumbnail downloads. A named User-Agent is sent to Wikimedia for proper API identification. Normal keyboard typing remains completely offline.

Verified on the Android 34 emulator: the search `happy` displayed `Vorschau 10/10` with ten loaded GIF thumbnails and no app errors; tapping the first tile opened the Android `ChooserActivity` with the actual downloaded animated GIF attachment, and the cached file was 869 KiB. The phone SSH endpoint was unreachable from Nitro, and only the emulator—not the real Ulefone—has passed this acceptance. The Openverse catalog remains small and quite unlike GIPHY's general reaction GIF library. Further handset testing and real-world network quality validation are needed before claiming full production reliability.

The owner found the Wikimedia/Openverse results unsuitable despite successful GIF file delivery. The content source was the actual defect: Openverse's GIF corpus heavily features educational/archival Commons animations, not relevant reaction memes, and adding more of the same results does not repair semantic search quality. Already verified: no-key Wikimedia query `happy` rendered in three columns on the Android 34 emulator without crashes, and the `Tenor-Web` action opened the exact official search path. ## November 7: long-press spacebar cursor tracking, editable caret, and next-word suggestions (v0.7)

Owner reported three concrete usability failures: the spacebar could not move the caret with a hold-and-horizontal-slide gesture; tapping into a joined word could trigger the host app's text-selection toolbar and hide the insertion caret; and the keyboard displayed no predictions before typing a letter unless the same word sequence had been learned already.

* Short spacebar taps insert one normal space. A hold of about a third of a second activates a horizontal cursor slider with haptic feedback. Swipes left or right move the insertion position in discrete grapheme-aware character increments using `InputConnection.getSurroundingText()` and `setSelection()`; old-editor fallback uses extracted text and DPAD key events. The gesture **never** inserts extra spaces when swiping. Cursor positions are clamped at text edges and avoid splitting surrogate pairs or attached combining accents. The separate left/right toolbar buttons use the same cursor-safe logic.
* A small local caret preview (`…left│right…`) appears whenever the editor contains text, including when the insertion position is at the beginning or end. When text is selected, it instead shows the selection length and can be tapped to collapse the selection to a visible insertion point. The keyboard asks compatible editors not to hide the caret via `setImeConsumesInput(false)`. The Android host app controls its own text-selection popup and caret rendering; an input method **cannot guarantee** that every unrelated app keeps its caret visible while the native popup is active. The supplemental caret marker remains under IME control and the spacebar gesture can reposition the host selection without changing text. Suggestions are suppressed when replacing a selection or editing inside a word, preventing accidental destructive completions while inserting missing spaces.
* German and English next-word suggestions now have a compact offline, context-dependent bigram/trigram baseline generated from Tatoeba sentence exports. The keyboard uses this as a fallback when the personal history has not observed the current context. As soon as the user confirms or selects words, the personal learned counts (with recency and explicit selection history) take priority. The same top three, most likely centered, are available even when the current word prefix is empty. Punctuation at sentence boundaries resets prior-context guesses to possible sentence starts. Everything is offline; no network usage occurs for typing or predictions.

**Build and acceptance:** test both the pure-Java cursor movement, boundary conditions, codepoint/combining handling, swipe accumulator, baseline ngram scoring, and pre-letter suggestions through JUnit; additionally perform real touches and Android `EditText` cursor-position checks in the API 34 emulator, verify no inserted extra spaces during swiping, successful space repair in a joined word, caret indicator during host text selection, and no service ANRs while loading the larger generic dictionary. Android normally auto-decompresses `.gz` assets, so the precompressed `.ngram` extension must remain unchanged. The app includes a cursor-position readout in its Settings test field to make these tests observable. The target physical phone has not been checked yet.

## November 7: priority German keys, English neural predictions and casing (v0.8.0)

Owner-requested priority layout: the QWERTZ letter keyboard now always displays an independent numerical row with 1 through 0. This row remains available in the text and symbol layouts, so switching to `?123` is not necessary for ordinary digits. A, O, U and S now respond to a short normal tap with the base letter and to an extended hold with the highest-priority German character: Ä, Ö, Ü and ß, respectively (shift/caps handled). Releasing a hold after two seconds inserts the preferred character directly with no popup, duplicate key event or extra click. To obtain a less common accent, hold the letter and slide **upwards**. This opens a submenu in the initial native popup, leaving rare accented forms out of the common interaction path. A dedicated pure-Java priority test covers all shift states, rare alternatives and the two-second hold threshold. The permanent number row and the umlaut long-hold behavior were verified using the actual Android 34 emulator and `adb` touch events; a scripted sequence produced the expected `Öüß`, while the original short A press/long A press produced an uppercase Ä when shift was active. The special-character submenu was also opened by a real upward slide without typing anything or crashing. The dedicated number row adds one key row above the normal QWERTZ layout; assess the resulting occupied screen height on the user’s device.

Neural predictions: Chime-SMS-2M by Luke Steuber, an Apache-2.0 reference implementation and CC BY-SA 4.0 quantized fixed-weight English word predictor, is now bundled inside the APK (`chime_en.ltc`, approximately 2.2 MB). A dependency-free Java CIFG-LSTM forward pass reimplements the published model for Android. The published checksum is verified at file acquisition; an internal LTCF CRC is verified before model use. The open-source inference produces the same reference predictions for `see you `, `I am ` and `hello wor`. Its output is ranked as an optional boost to the local German/English word counts, but **personal learning and explicit selections remain authoritative**, and neither the model nor its output changes text unless the user taps a suggestion. An on-device test verified the prompt `I am `, with `not` ranked in the middle. All inference runs in a dedicated, bounded background worker; no keystroke waits for it. The model can be disabled in the app settings.

Capitalization: fixed prefix casing now preserves every case pattern already typed, not merely whether the first letter is uppercase. German lexicon casing remains separate from last-used surface form; explicit prefixes override suggestions (e.g. `hau` becomes `haus`, `Hau` becomes `Haus`, `HAU` becomes `HAUS`). Automatic shift is recomputed after sentence punctuation and cursor edits, respecting explicit shift/caps. Language routing now considers recent nearby words, including those in the previous sentence: German `hallo. ` keeps German results, while `I am ` routes to Chime English. The baseline German/English corpus results are also filtered by that context language. A regression suite checks case fidelity, sentence boundaries, bilingual routing, known Chime predictions, corrupt checkpoint rejection, and personalized preference strength. The German-language case handling cannot be guaranteed in every third-party editor (some control their own capitalization), but the keyboard does not alter user-typed letters without an explicit selection.

Caution: Chime supports only English. German is still ranked with the local corpus ngram model and personal usage. Nothing claims this is equal to or better than production Gboard; further natural-typing evaluation, battery observations, keyboard-user trials and actual handset tests are warranted. The English model's trained language distribution contains conversational sources and may show biases.


## November 7: actual German 20-word neural context, v0.9.0

The previous v0.8 keyboard used an English-only neural model, plus a German Tatoeba-based two/three-gram baseline. This was insufficient to track the meaning of longer German sentences. The v0.9 release now uses the published `youcoded/next-word-german` quantized one-layer LSTM checkpoint (`german_next_word.nwp`, 4,718,096 bytes, 23,990 vocabulary IDs, 128-dimensional embedding, 1,024 hidden units). It reads at most the last twenty complete German words in the current sentence. The predictor is fully on-device with a pure Java integer-quantized inference implementation verified against the published NumPy reference. It uses a dedicated background inference worker; keyboard touches remain independent of slow predictions. A CRC-like FNV-1a checkpoint verification rejects corrupt or unexpectedly formatted models. When the neural model fails, German n-grams and personal learning remain usable.

The model is combined with existing n-gram, word-frequency, and confirmed-user selection history. The German neural top-15 candidates are weighted by rank (initial score 60 dropping by 3.2 each rank) and the combined ranker returns the usual three words with the best centered. Personal choices remain a separate, strong positive signal; chosen words are never silently inserted or autocorrected. English continues to use the previously integrated Chime-SMS-2M model. The language route adapts to preceding German/English words. The existing personal SQLite database has not been reset or migrated for this change. Case and number/umlaut keyboard controls are unchanged. ASCII approximations such as `wuerde`, `moechte`, `fuer` are mapped to real German vocabulary forms only when the model knows that form, avoiding wholesale alteration of the user's typed text.

### Measured evidence and limitations

The model author reports improved top-three next-word predictions when blended with the author's own n-gram corpus, on held-out Common Voice and web tests; those scores do not apply directly to this app. A separate current app benchmark on 400 randomly selected Tatoeba German contexts (sampled from sentence IDs ending in zero, excluded from this app's initial even-line n-gram subset) measured baseline top-three recall of **74/400 = 18.5%** and neural-fused recall of **114/400 = 28.5%** at weight 45, or **117/400 = 29.25%** at weight 65. The tested blended weight for this release is a nearby value 60, not exactly either measured point. The baseline initially had a duplicate candidate bug, discovered and fixed before benchmarking. Because the publisher may have trained on other nearby Tatoeba sentences and some near-duplicates can occur, these are *not* guaranteed independent test cases or everyday texting scores. Do not claim near-Gboard accuracy or predictiveness for every kind of message. The neural inference itself was tested on the exact `ich habe` -> `mich`, `mir`, `die` and `ich würde gerne` -> `wissen`, `mal`, `eine` top results reported by the model's independent NumPy reference.

Emulator integration verified that the model loads successfully alongside Chime English and the local German/English n-gram baseline, with no crash. Actual on-screen German text `ich habe ` showed `mich` centered. The app's memory use and inference time on an actual Ulefone have not been measured; desktop standalone Java tests initially showed around 20–100 ms for common context inference after startup and about 0.4 seconds on the cold `ich bin` context, with cached results much faster. Neural inference always runs outside the UI thread and stale requests are dropped; it should not delay character entry. The desktop benchmark is **not** a measured phone latency bound.

Source: https://huggingface.co/youcoded/next-word-german . License and metadata in `third_party/german-neural/` and `THIRD_PARTY_DATA.md`.

### Contextual German capitalization validation (v0.9.0)

A late emulator acceptance check revealed that the old German lexicon, which includes canonical noun forms such as `Wissen`, caused the next-word suggestion `Wissen` after `ich wuerde gerne`, where the user requires the lowercase verb `wissen`. The fix adds a **corpus-derived, context-specific German case ranker** (`de_word_case.gcase`, about 0.84 MB), using only aggregate uppercase/lowercase token and word-pair counts from the already attributed public Tatoeba German sentence corpus (about 785,673 sentences). These contextual statistics are distinct from personal learning and are loaded on the existing background worker. The ranker preserves all explicitly typed prefix letters, capitalizes sentence starts, and uses previous-word capitalization counts when sufficiently supported, falling back to the token's overall case distribution. As examples, the corpus contained 102 lowercase and no uppercase `wissen` after `gerne`; `Haus` was uppercase in 4,913 of 4,917 non-sentence-initial appearances; `Morgen` is uppercased after `guten`, lowercased after `bis`; `Essen` is more often capitalized after `das` but lowercase after `gerne`. The current emulator verified that `ich wuerde gerne ` now displays lowercase `wissen` as the central suggestion. Tests include these cases, mixed explicit-capitalization patterns, and unchanged personal word DB integrity. No model claims perfect part-of-speech disambiguation; German morphology is broader than this approach.


## November 7: fast typing and asynchronous predictions (v0.10.0)

The owner reported that the v0.9 release's key entry was slow and that suggestions did not feel connected to previous typing. Code inspection revealed that each character performed repeated synchronous `InputConnection` calls across Android's process boundary, executed a full personalized prediction on the IME's main thread, sometimes rebuilt the entire keyboard after Shift, and triggered another prediction from every editor selection notification. The previous keyboard also had high allocation pressure when looking for typo matches with long or uncommon prefixes. A synthetic sequence of thirty on-screen `A` taps on the Android emulator measured approximately **sixty-eight milliseconds average UI input time**, with garbage collection pauses reported by Android. That was not a physical-phone latency measurement.

The new input architecture commits a typed letter first, and schedules suggestions after a brief pause. A single `getSurroundingText` request retrieves before-cursor, after-cursor and selection state at once; older Android input connections fall back to individual queries. This snapshot also updates the caret indicator and Shift state without further round trips. The direct UI key callback does **not** perform dictionary lookup or neural inference. A dedicated personal-ranking worker computes quick suggestions and a separate, bounded background neural worker refines them once the user pauses; older results are rejected using a request revision. The neural task is prioritized shortly after word boundaries, not after every keystroke while the user is typing fast. The keyboard's rows are never reconstructed just because Shift changes; the existing letter labels are changed in place. The caret indicator always reserves the same vertical space, so key positions do not jump after the first letter. Selection callbacks coalesce into the same delayed update. Suggestions cannot be accepted from an obsolete input revision.

The personal dictionary now memoizes a bounded, relevance-ranked shortlist for common one-to-three-character prefixes while always admitting words learned in the current conversation context and candidates offered by the neural model. Long nonsensical prefixes no longer trigger a full first-letter-wide typo scan; typo recovery uses a shared-prefix filter and hard work limits. A Nitro standalone benchmark showed cached `ha` predictions below a millisecond and long nonsense prefixes only a fraction of a millisecond; this does not measure phone UI latency. The bundled dictionaries used to take approximately two seconds to load and sort the first prefix index on Nitro. That initialization now happens entirely on a background worker. SQLite learning is restored on its serialized disk executor, with a bounded catch-up journal for confirmed words, selected suggestions and undos that arrive while the restore is being prepared. User learning and the existing database are preserved. Database teardown flushes queued writes before closing, without stopping the IME main thread. All normal typing and prediction remain offline.

`KeyboardPerf` logs contain **only aggregate timing and count metrics** every twenty-five typed characters, not any actual text or sensitive input; this helps compare emulator and phone responsiveness. It is a debug-only evaluation interface, not analytics or telemetry. Private/password fields still skip language suggestions.

**Remaining:** install the signed debug APK in an emulator, measure actual key-commit and UI callback latencies, validate selection/suggestion ordering, check a no-predictions/private-field editor, verify that user learning survives a cold start and model switch, and test the downloaded build on the real phone before claiming satisfactory responsiveness or production reliability.

## November 7: strict owner-history-first prediction and recent weighted next-word learning (v0.12.0)

Owner found that German words were proposed after the English contraction `let's`, and that neural/corpus guesses overrode combinations the owner had already typed repeatedly. Investigation confirmed the code was adding neural and generic scores to personalized word-transition scores instead of enforcing personal-history priority. The owner specified a strict decision rule: **if a previously confirmed next word exists after the last word, return the most likely personally used continuation instead of generating other suggestions with a generic language model**. When a typed word-prefix contradicts every previously observed continuation, a new word-completion fallback is permitted. A word that has been typed but has never been followed by a confirmed next word is not enough to infer the intended continuation.

The new `PredictionModel.personalNext()` hard-selects only previously confirmed personal next words for the immediately preceding word, including at empty prefixes. Generic ngram and neural scores cannot overrule this rank. A matching two-word history serves only as a minor tie-breaker. If the preceding word has never had an observed next word, or a typed prefix matches none of those observed continuations, the engine uses corpus/neural fallback. Generic fallback filters purely German dictionary words from English predictions and vice versa, while retaining personally typed words and internationally familiar terms. The `LanguageContext` detector recognizes `let's`, `let’s`, `don't`, `we're`, `it's` and other contractions as strong English cues even when the preceding text was German or contained a language-neutral `okay`. The two phrase-completion generators and the neural scheduling path now enforce the same personal-first decision; an already observed continuation never triggers unnecessary neural inference. **Never storing or displaying a generic prediction counts as having typed it; only actual confirmed delimiters and explicit taps create personal history**.

For each preceding word, a new bounded recent-history window records only the latest forty-eight confirmed next-word tokens in the private SQLite database, never full messages. `PersonalNextWords` computes an exponentially weighted recent share of these observed transitions (seventy-five percent retention per older observation), and combines it with lifetime pair frequency. The recent component starts at low weight when only one new transition is known and grows toward seventy percent as additional real observations arrive. Thus long-standing high-frequency usage remains initially favored, while repeatedly choosing a different next word can take over after just several confirmations. This is a moving average across actual *uses*, not elapsed calendar days; it adapts even if the user changes habits within a single conversation. Recent history is updated on confirmation, stored transactionally beside existing pair/trigram counts, and restored on reboot. A precise undo also restores any oldest entry evicted from the full window. The schema migration from earlier versions adds only the `next_recent` table and preserves every existing word, pair, triple, explicit selection, clipboard and historical count. Older SQLite versions never recorded exact observation order, so it is impossible to reconstruct the *past* recency trend from old lifetime counts. Previously learned lifetime counts remain immediately active; new recency evidence starts accumulating after this version is used.

When a personally observed previous-word context has only one valid continuation, only that single candidate appears in the word bar; the other positions remain blank instead of being filled by invented model guesses. The existing middle position still displays the strongest candidate. Multiword suggestions obey the same rules. This deliberate choice prioritizes correctness over always filling three positions with generic words. The user can continue typing a different prefix to obtain new word-completion candidates.

New regression tests verify: `Okay, let's ` triggers English; smart and straight apostrophes share the same learned history; a personally selected `let's → go` cannot be overridden even by an artificially huge German neural score; unlearned contexts fall back to language-appropriate word completion; one new observation does not immediately overwhelm a hundred older confirmations; several new observations do; observation windows round-trip through the serialized format; and the editor's undo leaves older moving-average observations intact. These tests are pure Java and do not require a model server. Full Android emulator acceptance must also verify the schema upgrade from the old release, real typing, no crashes and preservation of personal data before distributing the APK.

### November 7: robust bidirectional spacebar trackpad (v0.12.0)

The owner reported that holding and sliding the spacebar moved the cursor left, but not right in the real Android app. A complete source-level pass through the keyboard modules identified cursor gesture fragility in `AdaptiveKeyboardService.spaceTouch()`, `SpaceSwipe` and `CursorNavigator`: the previous implementation ran `getSurroundingText(3000,3000,0)` or a second extracted-text query **for every nonzero movement event**, issued an additional `setImeConsumesInput(false)` on every successful motion, reset its movement origin to the latest touch position after the long-press delay, and assumed `SurroundingText.getOffset()` was always a valid non-negative absolute index. Android explicitly permits `getOffset() == -1`, and individual editor calls may take an IPC round-trip or time out. These assumptions were wrong in nonstandard text editors and could lose rightward motion when input events arrived slowly.

The new cursor implementation captures a single, validated, small surrounding-text snapshot at the beginning of each continuous spacebar gesture, then computes left **and right** positions locally and issues only `InputConnection.setSelection()` for movement. It handles text boundaries and Unicode supplementary characters, refuses to create invalid absolute positions when Android reports an unknown offset, and falls back to properly paired DPAD key-down/up events for editors that lack reliable selection APIs. Holding-space gesture activation always uses the original finger-down position, not the finger's position after the 330 ms delay. Android's parent view is told not to intercept touch gestures; the original touch pointer is tracked safely, and gesture movement no longer triggers a redundant suggestion refresh on every selection callback. A single refresh follows release. Changing editors, closing the IME or switching keyboard layouts cancels any active gesture so a stale snapshot cannot reposition another editor's cursor.
