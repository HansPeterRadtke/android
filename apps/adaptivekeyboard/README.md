# KontextTastatur — local adaptive German Android IME

A standalone Android InputMethodService for German QWERTZ typing, focused on user-confirmed contextual predictions. This project is developed in a separate Android repository worktree to avoid disturbing the existing Android clients.

## Implementation and privacy contract

- Three independent suggestions, in rank order **second, first, third**, so the most probable appears in the center. No forced autocorrection or automatic acceptance.
- Predictions are based on mixed German and English lexical frequency and user-confirmed word frequency, previous-word and previous-two-word context, and exact user-selected prefix/word combinations. Word forms are keyed with `Locale.GERMAN` case folding; user-confirmed spelling and canonical German noun casing are preserved.
- The UI calls `predict` after a text insertion; a visible or discarded suggestion does **not** increase any count. A typed word is learned only when the IME sees a delimiter or the user explicitly taps a suggestion. The latter replaces the typed prefix, inserts a space and records the exact selection separately. Immediate deletion of a delimiter attempts to undo the most recent learning event.
- Personalization is locally persisted in `learned.db` (SQLite) in the keyboard app's private data directory, without raw typed sentences, text-field dumps or cloud syncing. Database writes are serialized on a worker thread. Android backup is disabled. Only local context words and count statistics are retained, including a prefix when the user explicitly selects a completion. Other apps can access keyboard output only through the normal Android input method API.
- Passwords, sensitive text variations, URL/email fields, `NO_SUGGESTIONS`, `IME_FLAG_NO_PERSONALIZED_LEARNING`, and non-text fields disable learning and suggestions. Manual private mode disables both learning and suggestions globally. Users can explicitly reset learned data; the bundled lexicon remains.
- German and English completion, user-typed capitalization (lowercase, uppercase or all caps), contractions, learned rejection of suggestions contradicted by further typing, German umlauts, sharp S, uppercase ẞ, symbols, alternate accented letters via long press, emoji categories, cursor movement, copy/cut/paste, manual clipboard pinning and local clipboard history (twenty entries, up to three thousand characters) are supported.
- GIF search is only performed after explicitly entering the GIF search panel and pressing search. No API key is needed for the default Openverse search of Wikimedia Commons animated GIFs. GIPHY is an optional, much broader provider requiring its own user-provided API key. No secret key is included in the APK. GIF thumbnails are fetched from the selected provider, and a selected GIF is committed with Android `InputConnection.commitContent` using a read-only `content://` provider if the receiving app advertises `image/gif` support. Otherwise the public GIF link is committed as text. Original data and provider attributions appear in the settings. GIF search and sharing require connection; typing and prediction do not.

## Build and install

From the Android repository root:

```sh
ANDROID_HOME=/data/install/android-sdk ./gradlew :apps:adaptivekeyboard:assembleDebug
ANDROID_HOME=/data/install/android-sdk ./gradlew :apps:adaptivekeyboard:testDebugUnitTest
adb install -r apps/adaptivekeyboard/app/build/outputs/apk/debug/adaptivekeyboard-debug.apk
```

Open the launcher activity and enable/select `KontextTastatur` using the two system controls. Do not switch the owner's real-phone default keyboard without approval. Emulator testing uses API thirty-four and does not change any physical device.

## Required further acceptance

Test on the actual target phone, touch keyboard sizing, layout/rotation, selection replacement in other apps, IME field variations, private-learning guarantees, copy/paste permission behavior, persistent restore after process death, corrupted database handling, negative suggestion and latency benchmarks, and real GIPHY API and rich-content interoperability. A built APK and passing JUnit tests are **not** evidence of those unperformed tests. GIPHY integration requires a valid provider key and respect for the vendor's terms.

## Reference research

- Android `InputMethodService`, `InputConnection`, `EditorInfo`, `InputContentInfo`, `commitContent`, and clipboard access from developer.android.com. Code uses the Android API thirty-four SDK installed on Nitro.
- HeliBoard, FlorisBoard and FUTO Keyboard were reviewed as alternative IME architectures; all are significantly larger codebases than the tested standalone word-learning engine. None was imported, forked or claimed to pass its test suite.
- Raspi KnowMoreDiRT FileDB semantic search was queried for Android keyboard prediction and mobile touch design; no directly applicable keyboard source was returned. The complete original index is preserved. The owner's Infra Android GUI rules were used for immediate tap feedback and conservative feedback semantics.
- See `THIRD_PARTY_DATA.md` for the generated German lexicon's CC BY-SA/CC0 source licensing and offline generation recipe. Do not redistribute input archives or paid/uncleared research papers.

## November 6 emulator acceptance

The Android API 34 emulator (Nitro) was used for actual `InputMethodService` registration, IME selection, keyboard rendering in `SettingsActivity`, touch entry, completed-word SQLite persistence, and a separately verified tap on the middle suggestion. With `haus` in the editor, tapping the center suggestion inserted `Haus ` and the app SQLite recorded `token=haus`, `selected=1` and the exact `prefix=haus`. `PRAGMA integrity_check` returned `ok`. Twelve+ JVM tests cover contextual ranking, rejected predictions, explicit selections, German word boundaries, typo fallbacks, retrievable saved state, and undo. The Android emulator was not a physical phone. No provider credential was configured, so real GIPHY search and MIME interoperability were not verified. No user data was imported or reset.

Caveats: This is a tested first keyboard release, **not** feature parity with Gboard. Gesture typing, multilingual switching, a verified cloud GIF provider integration, and real handset touch-size benchmarks are not implemented/verified. The clipboard retains at most twenty user-pinned items and requires explicit pinning. The ranker is count-based and not a trained transformer; quality still needs measured long-term usage evidence.

## Prebuilt emulator-tested Android package

The signed debug APK is checked in under `release/kontexttastatur-0.1.0-debug.apk`, alongside its SHA-256. It is deliberately a development/test build, not a production Play Store release. It can be sideloaded after allowing installs from the chosen file source; choose the keyboard in Android system input method settings. It never changes the default IME automatically.

## November 6 owner feedback correction (version 0.3.0)

The owner reported incorrect lowercase handling, German-only suggestions and inadequate prediction quality, and challenged the need for a GIPHY API key. Corrections: the English `wordfreq` lexicon is bundled alongside the German lexicon; short English contractions are tokenized; mixed-language ranking uses nearby lexical-language evidence and real personalized bigram/trigram counts; suggestions now match the exact uppercase/lowercase/all-caps form of the typed prefix; explicit selection at a long prefix is learned for every shorter prefix as well; continuing to type a contradictory character adds a *negative* rather than a positive candidate observation. Existing SQLite learning history is preserved by an additive schema migration (v1 to v2), including the personal word sequences. The default GIF panel searches Openverse/Wikimedia without authentication; GIPHY remains optional when the user provides a key. Openverse's results are mostly openly licensed educational/creative animated GIFs, not a substitute for GIPHY's reaction/media catalog. Search queries are sent only after the explicit GIF search button, never during ordinary typing. Anonymous Openverse requests are rate limited and depend on that service. A repository-based regression suite verifies these particular failures; on-device acceptance is recorded separately.

## Version 0.3.0 observed acceptance

The latest release adds timestamp-based choice recency to user-confirmed prefix decisions. Selection counts alone did not distinguish the most recent candidate when old selections conflicted. The SQLite migration to schema version three adds `last_used_ms` to word rows and `last_selected_ms` to choice rows without dropping any previous user tables or rows. Android emulator upgrade from schema version two to three verified preservation of all existing word, pair, triple, choice, rejection and clipboard row counts and `PRAGMA integrity_check=ok`. Upgrades directly from schema version one are supported by the same additive migration path but not separately retested in the latest subrelease.

The original Android API thirty-four emulator was used to screenshot the actual prediction bar, select `hello` after typing `hell`, verify that it inserted `hello `, and confirm that `hello` became the central prediction after typing the same prefix again. After force-stopping and restarting the keyboard, `hello` remained the central prediction, proving that the latest selected-prefix timestamp persisted and restored. Tests also confirmed lowercase output and bilingual suggestions in actual UI. The earlier test mistakenly tapped an alternative suggestion to `hell` and thus taught it repeatedly; on-device rank inspection identified that and validated the repaired selection preference.

The new anonymous GIF panel was exercised in the emulator: searching for `happy` returned Openverse/Wikimedia results without entering any API key. Some Openverse thumbnail URLs returned an HTTP 424 despite the original Wikimedia GIF being accessible; a bounded original-GIF fallback and visible generic icon for unavailable previews were added. The user's phone and a third-party target with rich GIF support were not tested. GIF licensing/attribution varies by result, and the openly licensed catalogue is not as rich as GIPHY.

Ranking still needs objective evaluation on real non-sensitive personal typing sessions; an offline count-based model should not be presented as proven equivalent to production Gboard prediction quality. The user can continue typing without autocorrection. Personal learning is confined to the app SQLite database; GIF requests only transmit the user's explicitly submitted search term.

## November 7: GIF sharing correction, version 0.4.0

Owner reproduced the broken GIF behavior by posting two Wikimedia Commons description-page links, page IDs 7419763 and 7399044, in a conversation. The original fallback in `AdaptiveKeyboardService.sendGif()` inserted `gif.link` via `InputConnection.commitText()` when the receiving text field did not advertise support for `image/gif`. That was a fundamental format error: a landing-page URL is not an animated attachment. Both reported pages are real GIFs: `Scratch-Lissajous-nevit-01.gif` and `Scratch_Rainbow_nevit.gif`.

The corrected behavior is as follows. On tapping a result, the keyboard downloads and validates the original GIF bytes into its private cache. If the receiving editor advertises image support, it attempts `InputConnection.commitContent` with a read-only temporary URI grant. Otherwise, or when the editor rejects the request, it launches the Android binary image sharesheet with `ACTION_SEND`, MIME `image/gif`, `EXTRA_STREAM` as a `content://` URI, `ClipData`, and `FLAG_GRANT_READ_URI_PERMISSION`. **It never silently inserts the Wikimedia landing-page address.** A long-press on a result also offers **share GIF as a file** and **copy GIF to clipboard as image data**. The custom content provider reports filename and size via `OpenableColumns`, enforces read-only access and only exposes matching cached `.gif` items. The app and user must still choose a destination in Android's sharesheet: the keyboard cannot force rich insertion into apps which do not implement Android image-keyboard integration. Sharing to a destination app may start a new conversation instead of adding the GIF to the existing text field. The keyboard does not claim otherwise.

**Verified emulator acceptance:** Android API 34, user-initiated `scratch` GIF search through Openverse; first result resolved to the user's *Scratch Rainbow nevit* GIF and was cached as a 13,877-byte GIF image, 180 by 661 pixels, matching Wikimedia's original metadata. Tapping that result from the plain-text Settings test input launched the system `ChooserActivity` with an `image/gif` ClipData payload, temporary read permission, and `ACTION_SEND` image attachment. Android's sharesheet displayed **Sharing image** and a proper visual preview of the GIF, not text or a Wikimedia link. `GifDeliveryPolicyTest` verifies that plain-text/unsupported editors route to binary sharing and that compatible MIME types take the direct path. Together with the unchanged prediction tests there are 25 passing JVM tests.

**Still not claimed:** attaching into the current ChatGPT input field, or end-to-end delivery to WhatsApp or another real messaging recipient, was not verified because this depends on the target app's support and user selection. It is not possible for an IME to make a plain-text-only editor accept binary GIF data just by sending more text. No real user messages were sent in testing.

## November 7: GIF preview-loading repair (v0.5.0)

Owner reported that GIFs still did not load. Analysis of the shipped code found a systematic failure: anonymous Openverse search returns `api.openverse.org` preview proxy addresses, which sometimes return HTTP 424, and the fallback rejected original GIFs above 1.8 MB. There was also one shared three-thread executor for search, previews and user-selected shares; a tap could wait behind up to eighteen thumbnail requests. Errors were silently presented as empty tiles.

The corrected version constructs Wikimedia's canonical `120px-*.gif` thumbnail URL when the original URL is a legitimate `upload.wikimedia.org` GIF, with a strict origin/path check and preservation of raw URL encoding. If Openverse search is unavailable or gives unusable results, its independent Wikimedia Commons image-information search provides a fallback. Thumbnail requests have shorter bounded timeouts and a small in-memory LRU; previews are downsampled for UI memory and `AnimatedImageDrawable.start()` enables animation on Android versions supporting it. Ten results are fetched initially, each tile always displays its name, and the toolbar reports real completed/success/failed thumbnail counts. Search, preview and user-selected GIF transfers now have separate workers, so an image-sharing tap does not queue behind background thumbnail downloads. A named User-Agent is sent to Wikimedia for proper API identification. Normal keyboard typing remains completely offline.

Verified on the Android 34 emulator: the search `happy` displayed `Vorschau 10/10` with ten loaded GIF thumbnails and no app errors; tapping the first tile opened the Android `ChooserActivity` with the actual downloaded animated GIF attachment, and the cached file was 869 KiB. The phone SSH endpoint was unreachable from Nitro, and only the emulator—not the real Ulefone—has passed this acceptance. The Openverse catalog remains small and quite unlike GIPHY's general reaction GIF library. Further handset testing and real-world network quality validation are needed before claiming full production reliability.

## November 7: reaction GIF discovery and provider UX (v0.6.0)

The owner found the Wikimedia/Openverse results unsuitable despite successful GIF file delivery. The content source was the actual defect: Openverse's GIF corpus heavily features educational/archival Commons animations, not relevant reaction memes, and adding more of the same results does not repair semantic search quality. Research verified that the public Tenor third-party programming API was terminated on June 30, 2026, although Tenor's official website still supports individual browser searches. GIPHY and KLIPY both offer curated, multilingual, contemporary reaction libraries; the GIPHY official developer portal issues free rate-limited API keys (about 100 calls/hour for beta), and the KLIPY developer portal issues keys but requires prior approval for custom integrations. The free Imgflip `/get_memes?type=gif` endpoint returned 100 popular templates but their media URLs were MP4 rather than GIF; full database search requires Premium. None of these offers a documented unrestricted, high-quality, anonymous general reaction-GIF API to embed in an unapproved third-party keyboard. Do not mislead the user by claiming Openverse is equivalent.

The keyboard's main GIF screen now explicitly separates the working sources. When the user configures their own GIPHY key, the keyboard uses GIPHY rather than Wikimedia by default. GIPHY searches omit the former hardcoded German-only language restriction, use the user's selected content rating with `r` as the default, retrieve 24 relevant results per page, offer further pages and trending without a query, and select a mobile-sized `fixed_width` GIF for sending instead of a potentially enormous original. The picker displays the required `Powered By GIPHY` attribution. The owner can select G, PG, PG-13 or R from the settings, and can enter/remove their key without touching the learning database. The settings contain an explicit action to open the official GIPHY developer portal. No provider key is included in the repository or APK; live GIPHY calls remain unverified until a valid user-owned key is configured.

Without a key, the picker openly labels the narrow Wikimedia-only source and also offers a `Tenor-Web` button that opens the official Tenor search website in the user's browser with the current search phrase. This is deliberately an **external website**, not a non-existent Tenor API and not integrated keyboard GIF transfer. The emulator resolved the browser intent to `https://tenor.com/search/happy-gifs`; its minimal WebView shell displayed a blank page, so successful webpage use with a real mobile browser has not been verified. Use normal Android browser tools to share/save the media if choosing this fallback. No scraping/unauthorized Google image API or someone else's API key was added.

The old one-line horizontal gallery was replaced with three columns and a vertically scrolling grid. Searching or browsing results hides the typing keys to make room for media; tapping `Tastatur` or the query field restores them for editing. The source switch immediately clears stale results, the clear-search action resets its request, and GIPHY has an explicit `Mehr GIFs` page action; Wikimedia cannot silently pretend it has more pages. Already verified: no-key Wikimedia query `happy` rendered in three columns on the Android 34 emulator without crashes, and the `Tenor-Web` action opened the exact official search path. The GIF-sharing fallback and private word statistics are unchanged. GIPHY URL construction and its official response schema are covered by synthetic tests; these do not constitute a real live provider test.

Documentation: https://developers.giphy.com/docs/api/ ; https://developers.giphy.com/docs/optional-settings/rating/ ; https://support.google.com/tenor/answer/10455265 ; https://docs.klipy.com/ ; https://imgflip.com/api ; https://tenor.com/search/ . Query providers' current terms before distributing a commercial or public keyboard.

## November 7: long-press spacebar cursor tracking, editable caret, and next-word suggestions (v0.7)

Owner reported three concrete usability failures: the spacebar could not move the caret with a hold-and-horizontal-slide gesture; tapping into a joined word could trigger the host app's text-selection toolbar and hide the insertion caret; and the keyboard displayed no predictions before typing a letter unless the same word sequence had been learned already.

* Short spacebar taps insert one normal space. A hold of about a third of a second activates a horizontal cursor slider with haptic feedback. Swipes left or right move the insertion position in discrete grapheme-aware character increments using `InputConnection.getSurroundingText()` and `setSelection()`; old-editor fallback uses extracted text and DPAD key events. The gesture **never** inserts extra spaces when swiping. Cursor positions are clamped at text edges and avoid splitting surrogate pairs or attached combining accents. The separate left/right toolbar buttons use the same cursor-safe logic.
* A small local caret preview (`…left│right…`) appears whenever the editor contains text, including when the insertion position is at the beginning or end. When text is selected, it instead shows the selection length and can be tapped to collapse the selection to a visible insertion point. The keyboard asks compatible editors not to hide the caret via `setImeConsumesInput(false)`. The Android host app controls its own text-selection popup and caret rendering; an input method **cannot guarantee** that every unrelated app keeps its caret visible while the native popup is active. The supplemental caret marker remains under IME control and the spacebar gesture can reposition the host selection without changing text. Suggestions are suppressed when replacing a selection or editing inside a word, preventing accidental destructive completions while inserting missing spaces.
* German and English next-word suggestions now have a compact offline, context-dependent bigram/trigram baseline generated from Tatoeba sentence exports. The keyboard uses this as a fallback when the personal history has not observed the current context. As soon as the user confirms or selects words, the personal learned counts (with recency and explicit selection history) take priority. The same top three, most likely centered, are available even when the current word prefix is empty. Punctuation at sentence boundaries resets prior-context guesses to possible sentence starts. Everything is offline; no network usage occurs for typing or predictions.

**Build and acceptance:** test both the pure-Java cursor movement, boundary conditions, codepoint/combining handling, swipe accumulator, baseline ngram scoring, and pre-letter suggestions through JUnit; additionally perform real touches and Android `EditText` cursor-position checks in the API 34 emulator, verify no inserted extra spaces during swiping, successful space repair in a joined word, caret indicator during host text selection, and no service ANRs while loading the larger generic dictionary. Android normally auto-decompresses `.gz` assets, so the precompressed `.ngram` extension must remain unchanged. The app includes a cursor-position readout in its Settings test field to make these tests observable. The target physical phone has not been checked yet.
