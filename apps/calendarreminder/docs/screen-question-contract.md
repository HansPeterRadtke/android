# Raspi Calendar — phone screen contract

User question on opening: **What is my next appointment, and will my phone remind me?** Show the next scheduled event clearly at the top, with date/time and title. Show near-future agenda below; mark last synced time and genuine sync failures, not fake live status. Primary action: Sync now (acknowledge immediately). Secondary action: Connection settings (hidden by default). When no events, visibly distinguish empty valid calendar from never synced or unreachable server. When permissions deny notifications or exact alarms, show a prominent blocker + actionable permission button. The product may only access its own cached events and dedicated Raspi HTTPS API, and must NEVER query Android calendar provider/Etar or Android Google accounts.

Screens: Overview (next event; status; Sync now; upcoming); Settings (server URL; token; timing; Save & sync). Standard touch targets >= 48 dp. Text uses sp. The display is a native Android UI, not a webview; status, timestamps and buttons respond within 100ms; background sync never blocks UI. Events are read-only in first release: write operations remain Google Calendar/Raspi-side. Users must be able to disable reminders without deleting events (notification permission or app settings).

## Automatic update contract (October twelve)

On launch or after initial pairing, Android starts an ongoing foreground calendar watcher without requiring the user to press Sync. Android shows one low-priority persistent notification for the live connection. The server long-polls for content changes and sends an immediate revision; the app downloads a complete snapshot and atomically replaces the cache and schedules local exact alarms. On reboot or application update, the receiver attempts to resume the live connection. Android can restrict foreground service starts or connectivity under device-specific power policies: the screen must report live status honestly, and Android JobScheduler retains the delayed periodic fallback. The **Check connection** button is troubleshooting only, never a required step after creating an appointment. Users can disable/re-enable the continuous listener in Settings. No calendar provider or Google account permissions are ever requested.
