# Raspi Calendar — phone screen contract

User question on opening: **What is my next appointment, and will my phone remind me?** Show the next scheduled event clearly at the top, with date/time and title. Show near-future agenda below; mark last synced time and genuine sync failures, not fake live status. Primary action: Sync now (acknowledge immediately). Secondary action: Connection settings (hidden by default). When no events, visibly distinguish empty valid calendar from never synced or unreachable server. When permissions deny notifications or exact alarms, show a prominent blocker + actionable permission button. The product may only access its own cached events and dedicated Raspi HTTPS API, and must NEVER query Android calendar provider/Etar or Android Google accounts.

Screens: Overview (next event; status; Sync now; upcoming); Settings (server URL; token; timing; Save & sync). Standard touch targets >= 48 dp. Text uses sp. The display is a native Android UI, not a webview; status, timestamps and buttons respond within 100ms; background sync never blocks UI. Events are read-only in first release: write operations remain Google Calendar/Raspi-side. Users must be able to disable reminders without deleting events (notification permission or app settings).

## Background updates and notification behavior (October twelve)

The current Android implementation uses JobScheduler for background synchronization instead of an ongoing foreground service. It must not display a permanent "running in background" notification. Android may defer background synchronization; show accurate freshness information rather than implying immediate propagation of changes. Previously synchronized events use locally scheduled Android alarms. On app resume, request synchronization and check scheduled alarms. These constraints must not be concealed from the user.

For every real appointment alert, expose three distinct actions in the notification shade: **Acknowledge**, **Snooze**, and **Dismiss**. The event-details view must also contain independent **Acknowledge event** and **Dismiss notification** controls. The notification body itself opens the event, so a redundant "View event" action must never displace Dismiss. Dismiss removes only the current notification without marking the event acknowledged; Acknowledge stores acknowledgement and clears the notification; Snooze schedules a subsequent reminder. The event remains in the app's history regardless. Test both action labels and these separate effects. No unrelated modifications to syncing, alarm timing, or Etar isolation should be required for this UI fix.
